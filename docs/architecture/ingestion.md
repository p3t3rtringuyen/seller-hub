# Ingestion engine

Task P3-INGEST. Code: `packages/ingestion` (engine, no queue dependency), `apps/worker/src/ingest.ts` (BullMQ,
Redis, Postgres, S3 binding), `apps/web/app/(app)/settings/sync` (status screen). Frame: ADR-0008 and its Gate 2
amendment, ADR-0006 (clients and limiter), ADR-0009 (storage, retention), D53 v1 default, D57 a (Ads v1 reports
only, no Reporting v3), D58 a (Marketing Stream v2 seam), D62 a (refresh after write), D64 a (retention), D11 (no PII).

Table names: the P3-INGEST prompt said `raw` schema and `core.sync_state`; the data model fixed `ingest.*`
(`docs/data-model/README.md` §1): `ingest.sync_states`, `ingest.job_runs`, `ingest.raw_objects`, `ingest.inbox`.
The DDL came with the platform migrations; this task added none.

## 1. How it fits together

```
 modules/<m>/src/sync/<k>/*.sync.ts ─┐
 modules/<m>/src/jobs/<k>/*.job.ts  ─┼─ pnpm gen ─► apps/worker/src/registry.generated.ts
 modules/<m>/src/commands/<k>/*.command.ts ┘            │
                                                        ▼
 ingest.sync_states ◄── scheduler tick (1/min, leader lock) ──► ingest.job_runs (one row per run, resumable)
   next_run_at, cursor        │                                         ▲
                              ▼                                         │ state machine, one step per call
                   BullMQ: ingest.interactive | ingest.scheduled | ingest.backfill ──► engine.processRun
                                                                        │
                      SP-API / Ads clients (token buckets, 429 retry) ◄─┤──► object store (raw/…) ──► parse ──► upsert
```

- **The registry** is generated by `tools/registry` (P3-SCAFFOLD): it globs `*.sync.ts`, `*.job.ts` and
  `*.command.ts` (BACKLOG §1.2), fails `pnpm gen` on duplicate keys, and writes `registry.generated.ts` for the
  worker. `toIngestDefinitions` (`packages/ingestion/src/definitions.ts`) then checks what a glob cannot: the family,
  the functions it needs, the schedule syntax, and that every `operations` entry is in the client allow-lists
  (`SP_OPERATIONS`, `ADS_OPERATIONS`; a v0 Ads operation must be a named exception, D53). The worker refuses to start
  on a bad registry.
- **The scheduler** is DB-driven. `ingest.sync_states` has one row per (seller account, sync key, scope). Scope is a
  marketplace id, an Ads profile id, or `''` for an account-wide sync (`scopeKind`). Once a minute, under a leader lock
  (`ConcurrencyGate`, key `ingest:tick`), the tick claims due rows with `FOR UPDATE SKIP LOCKED`, gives each a lease
  (`leaseMs`, 2 h: a row whose run never finishes becomes due again), creates a run and enqueues it. Every ten
  minutes the tick also creates rows that are missing for new accounts and definitions, each starting at a random
  offset inside the definition's `jitter`, and pauses or resumes syncs from the connection state the directory reports.
- **Fairness**: one Redis semaphore per (seller account, family), default 2, `concurrency` on the definition
  overrides it. A run that cannot take it is delayed 5–30 s; it does not fail. Amazon pacing is the client limiter's job.
- **Priority**: three queues with their own worker concurrency (interactive 4, scheduled 4, backfill 2) and a BullMQ
  priority inside each (1, 5, 10). Refresh-after-write and "Refresh now" are `interactive`; backfill is last.
- **System vs scoped access**: the worker holds two connections. `sh_app` (RLS) serves every run step through
  `withScope`. `sh_owner` is used only for the scheduler's cross-tenant claim of due ids, creating missing sync-state
  rows, pause/resume, partition maintenance, and `SellerDirectory.listTargets`. Nothing else reads across tenants.

## 2. A run is a resumable state machine

`ingest.job_runs.state`: `requested → processing → downloading → parsing → upserting → done | failed | cancelled`.
Every call of `engine.processRun` does one bounded step and returns `{ done }` or `{ delayMs }`; the worker
re-enqueues delayed work with a new job id (`<runId>-<step>`). No worker ever sleeps.

| Family | `processing` | What survives a crash |
|---|---|---|
| `paged-pull`, `sync-read` | one `fetchPage` per iteration; rows and the next page token commit in ONE transaction | the page token (`sync_states.cursor.runs[runId].nextToken`) |
| `spapi-report` | `createReport` once, then `getReport` polls (30 s) | `amazon_request_id` (never re-created), then the landed document |
| `ads-report` (v1) | `AdsApiv1CreateReport`, `AdsApiv1RetrieveReport` polls | `amazon_request_id`, then the landed parts |
| `ads-export` | `CampaignExport` / `AdGroupExport` / `AdExport` / `TargetExport`, `GetExport` polls | `amazon_request_id`, then the landed file |
| `data-kiosk` | `createQuery`, `getQuery` polls, `getDocument` | as above; needs a `DataKioskPort` (see §7) |

After `downloading` the document is in object storage (`raw/{tenant}/{sellerAccount}/{syncKey}/{yyyy}/{mm}/{dd}/{runId}/{part}`,
indexed in `ingest.raw_objects` with sha256 and expiry) and parsing/upserting read it back from there, so a resumed
run never asks Amazon for the report again. Upserts run in batches (`batchSize`, 500) inside one scoped transaction
per page or per document.

Cursors (ADR-0008 decision 6): on success the sync stores `cursor.lastUpdatedAfter = run start − cursorOverlapMinutes`
(and `windowEnd` for windowed syncs); the next run reads it from `ctx.cursor`. A scheduled window is `lookbackDays`
back from today (restatements converge), extended back to the last `windowEnd` after a gap, never longer than
`maxRangeDays`. There is no schedule that re-pulls everything. `nextCursor` overrides the default.

Failure policy (decision 11):

| What happened | What the engine does |
|---|---|
| 429 / `AmazonThrottledError` / `LocalRateLimitError` | **delay**, honouring `retryAfterMs`; counted in the last-run marker as `throttles`; not an attempt; fails only after 200 delays |
| `ConnectionNeedsReauth` | pauses every sync of that API for the account (`paused`, reason `needs_reauth`), run `failed`, no retry; resumes when the directory reports the connection healthy |
| retryable Amazon error or an unknown error | backoff 30 s × 2^n (±25 %), at most 4 attempts, then `failed` |
| non-retryable (validation, auth, report FATAL) | `failed` at once |
| run `failed` | `sync_states.status = failing`, `consecutive_failures + 1`, next try after a capped backoff; rows committed by earlier pages stay |

`error_detail` holds a sanitised message (500 chars, no stack, no bodies). A worker that dies mid-run leaves a run
that stops moving; the tick re-enqueues runs idle for 10 minutes and the run resumes from its state.

## 3. Writing a sync definition

A slice adds ONE file and touches nothing shared. Default-export the result of the `define*` helper for the family
(helpers are in `@seller-hub/ingestion`; they only give the editor the type).

```ts
// modules/listings/src/sync/merchant-listings/merchant-listings.sync.ts
import { defineSpReport, parseTsv } from "@seller-hub/ingestion";

export default defineSpReport<ListingRow>({
  key: "listings.merchant-listings",          // starts with the module name; unique
  family: "spapi-report",
  scopeKind: "marketplace",                   // one sync state per marketplace the account sells in
  schedule: { every: "6h", jitter: "30m" },   // omit for on-demand only
  appliesTo: { api: "sp", accountTypes: ["seller"] },
  operations: ["reports.createReport", "reports.getReport", "reports.getReportDocument"],
  report: (ctx) => ({ reportType: "GET_MERCHANT_LISTINGS_ALL_DATA", marketplaceIds: [ctx.scopeKey] }),
  parse: (text) => parseTsv(text).map(toListingRow),
  upsert: async (ctx, rows) => { /* ctx.trx is scoped to the tenant and seller account */ },
});
```

The full working example is `packages/ingestion/src/demo/merchant-listings.sync.ts` (upserts `catalog.listings`).

Common fields: `key`, `family`, `schedule`, `appliesTo`, `scopeKind` (`account` | `marketplace` | `ads-profile`; Ads
families default to `ads-profile`), `window` (`lookbackDays`, `backfillDays`, `maxRangeDays`), `operations`,
`batchSize`, `concurrency`, `cursorOverlapMinutes`, `nextCursor`, `refreshEntities`, `upsert`, `description`
(shown on the status screen).

| Family | Extra fields | Notes |
|---|---|---|
| `paged-pull`, `sync-read` | `fetchPage(ctx, token)` → `{ rows, nextToken }` | read `ctx.cursor.lastUpdatedAfter` for incremental pulls; call Amazon only through `ctx.sp` / `ctx.ads` |
| `spapi-report` | `report(ctx)`, `parse(text, ctx)` | the document arrives gunzipped; `parseTsv`, `parseJsonRecords`, `parseXmlRecords` help |
| `ads-report` | `buildRequest(ctx)` (body of `AdsApiv1CreateReport`), `parse(parts, ctx)` | `parseCsvParts` for CSV (each part repeats its header); `ctx.window` is the date range |
| `ads-export` | `exportOperation`, `buildRequest`, `parse`, optional `reconcile(uctx, rows)` | `reconcile` sees every row of the snapshot: mark mirror rows that are gone (`deleted_at`) |
| `data-kiosk` | `query(ctx)`, `parse(text, ctx)` | |
| `spapi-notification`, `stream` | `messageType`, `handle(pctx, message)` (use `definePush`) | no schedule; consumed from `ingest.inbox` (§5) |

Rules for the callbacks:

- Upserts are by Amazon's natural key and idempotent: a retry or a replayed window must converge (`ON CONFLICT DO UPDATE`,
  or delete + insert of the window inside the same transaction).
- Never log or store restricted data (D11); the clients refuse PII operations.
- Use the injected clients. They own rate limits (token buckets in Redis), retries and region routing (ADR-0006).
- Refresh after write (D62 a): give a `paged-pull`/`sync-read` definition `refreshEntities(ctx, ids)` and the command
  executor calls `scheduler.requestRefresh(scope, { syncKey, entityIds })` after a command succeeds (interactive
  priority, deduplicated per entity set). Without `refreshEntities` the call runs the whole sync now.

## 4. Operating it

```bash
pnpm --filter @seller-hub/worker ingest backfill --tenant <uuid> --account <uuid> --sync ads.sp-report-daily --scope <profileId> --from 2025-01-01 --to 2025-06-01
pnpm --filter @seller-hub/worker ingest refresh  --tenant <uuid> --account <uuid> --sync listings.merchant-listings --scope ATVPDKIKX0DER
pnpm --filter @seller-hub/worker ingest replay-inbox --tenant <uuid> --account <uuid>
```

- **Backfill** splits the range into windows of at most `maxRangeDays` (31), newest first, each its own run at
  `backfill` priority; a window that already has an open run is reused; `from` older than `backfillDays` is refused.
  A backfill never moves the live cursor.
- **Replay** of a failed push message resets its status; there is no dead-letter table (trap 14).
- **Retention (D64 a)**: the daily `ingest.maintenance` job creates partitions three months ahead and drops
  `ingest.job_runs` partitions older than 90 days and `ingest.raw_objects` partitions older than `SH_RAW_RETENTION_DAYS`
  (35). The bucket lifecycle rule that deletes the objects themselves is infrastructure (ADR-0009), not code.
- **Sync health** is a table query: `getSyncHealth(scope, db, definitions)` (`packages/ingestion/src/health.ts`) returns
  per-sync freshness (`fresh | stale | failing | paused | never`; stale = older than 2.5 schedule intervals), lag, next
  run, last-run rows/duration/throttles, and the 30 latest runs. The settings screen reads it through the BFF.
- **Dev without Amazon**: `SH_AMAZON_MODE=replay` makes the worker use the fixtures in `packages/amazon-*/fixtures`
  and fake credentials. Without replay and without a vault credential source, a run fails with a clear message.

## 5. Push sources: SQS stubbed (R7 not available)

`pollPushQueue({ sqs, db, source, parse })` reads a batch through the `SqsLike` port, inserts each message into
`ingest.inbox` (unique on `(source, message_id)`, so a duplicate is ignored), and deletes it from SQS **after** the
insert. `processInbox` claims `pending`/`failed` rows (up to 5 attempts) and calls the handler registered for the
message type; an error leaves the row `failed`; `replayInbox` resets it. A message with no handler is `failed` with
`no_handler`, so a missing handler is visible. Nothing in the worker polls a real queue yet: wiring an SQS client
(`@aws-sdk/client-sqs` behind `SqsLike`) and the destination settings is the R7 step below. Handlers must fetch
the object again before acting (`reference-patterns.md` §1.3): the notification can be stale.

### AWS setup for SP-API notifications (when R7 is available)

Reference: `refs/amazon/selling-partner-api-samples/use-cases/notifications` (CDK stack, queue policy).

1. **Queue** (per deployment, not per tenant): a standard SQS queue in the same region as the worker, SSE on, a
   redrive policy to a second queue only for messages the poller cannot parse (failed business processing stays in
   `ingest.inbox`). Visibility timeout 60 s.
2. **Queue policy**: allow Amazon's notification publisher to send:
   ```json
   { "Version": "2012-10-17", "Statement": [{
       "Sid": "SpApiNotifications", "Effect": "Allow",
       "Principal": { "AWS": "arn:aws:iam::437568002678:root" },
       "Action": ["sqs:SendMessage", "sqs:GetQueueAttributes"],
       "Resource": "<queue arn>" }] }
   ```
3. **Destination** (grantless, once per queue): `notifications.createDestination` with
   `{ name, resourceSpecification: { sqs: { arn } } }`; keep the `destinationId`.
4. **Subscription** (per seller account authorisation, per notification type): `notifications.createSubscription`
   with `notificationType` (types in `catalog/spapi/notifications.json`), `payloadVersion` and `destinationId`; check with
   `getSubscriptions`; `sendTestNotification` in the sandbox proves the path.
5. **Worker IAM**: `sqs:ReceiveMessage`, `sqs:DeleteMessage`, `sqs:GetQueueAttributes` on the queue only.
6. **App wiring**: an `SqsLike` over the AWS SDK, a `parse` that maps `payload.notificationMetadata.notificationId` to
   `messageId`, the type to `messageType`, and `payload.sellerId`/`applicationId` to the seller account scope
   (look it up through the connections module), then a `*.sync.ts` file using `definePush` per notification type.

Marketing Stream v2 (D58 a): same inbox and `definePush({ family: "stream", messageType: "<dataset>" })`; the handler
downloads the Parquet batch from the seller's own S3 and upserts facts keeping the highest `streamBatch.version`
(`catalog/ads/stream.json`). Not wired live: it needs the stream subscription calls (not in the Ads client) and
credentials for the seller's bucket.

## 6. Testing a definition

Use the engine's test kit (`@seller-hub/ingestion/testing`): `createTestEngine({ app, owner, definitions, targets })`
returns an engine on the Amazon mock transport (`@seller-hub/amazon-core/testing`), an in-memory queue and object store.

```ts
const h = createTestEngine({ app: t.app.db, owner: t.owner.db, definitions: [def], targets: [target] });
await h.scheduler.ensureStates();
h.amazon.transport.route({ method: "POST", path: "/reports/2021-06-30/reports" }, jsonResponse(202, { reportId: "R-1" }));
await h.scheduler.requestRefresh(scope, { syncKey: def.key, scopeKey: "ATVPDKIKX0DER" });
await h.drain();                               // runs the queue inline; delays are skipped
```

`packages/ingestion/test/engine.test.ts` shows the cases every definition should cover: the happy path from fixture,
an empty document, a 429 (`retry-after` above the client's cap reaches the engine), a crash and resume, a permanent
error, and another tenant seeing nothing. DB tests use `tryCreateTestDb()`; with `SH_REQUIRE_DB=1` a missing database fails.

## 7. Limits and open points

- **Data Kiosk** has no operations in the generated SP client (`tools/codegen/config/sp-allowlist.json` lacks
  `dataKiosk`). The family is implemented against a `DataKioskPort` and tested with a stub; the worker passes none, so
  a Data Kiosk definition fails with `kiosk_unavailable` until P3-CLIENTS adds the API.
- **Throttle counter**: `job_runs` has no `throttles` column, so the count lives in `sync_states.cursor.lastRun` (and
  `cursor.runs[runId]` while in flight). A column needs a migration that the migration discovery can see
  (`packages/ingestion/migrations/` is not globbed yet).
- **Ads report slots**: Amazon may allow one concurrent report per client app. The engine does not hold a lease across
  polls (a lease cannot outlive a worker); it relies on Amazon's 429 and the delay path. `createAdsReports().run()` (which
  does hold one) is unsuitable for a worker that must not block.
- **Credentials**: the worker needs a `CredentialSource` from the vault (P3-IDENTITY). `missingVaultCredentialSource` in
  `apps/worker/src/ingest.ts` is the placeholder; pass the real one to `startIngest({ credentials })`.
- **Directory**: `createDbSellerDirectory` reads `core.seller_accounts`, `core.seller_account_marketplaces`,
  `core.ads_profiles` and `core.connections` (read-only, owner connection). P3-IDENTITY may provide its own
  `SellerDirectory`; the port is the contract.
- **Sync-health route**: the BFF/API route and OpenAPI contract for `sync-health` and `sync/{key}/refresh`, the
  `sync.read` / `sync.refresh` permissions and the nav entry are outside this task's paths; the screen calls
  `/bff/v1/seller-accounts/{id}/sync-health` and shows its error state with Retry until they exist.
