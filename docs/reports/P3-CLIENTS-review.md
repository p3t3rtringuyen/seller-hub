## Must fix (before merge)

**M1 — D11 guard can be bypassed through report schedules.**
`packages/amazon-sp/src/restriction.ts:210-228`. `createReport` refuses PII report types, but
`reports.createReportSchedule` (generated, allow-listed with `"operations": "*"`) has no check, and
`reports.getReportDocument` is allowed unconditionally with `piiCheck.verifiedNoPii` because "the document id can
only come from a report our own createReport created" — false: schedules and `getReports` also yield document ids.
Failure: `sp.reports.createReportSchedule(scope, { body: { reportType: "GET_FLAT_FILE_ACTIONABLE_ORDER_DATA_SHIPPING", … } })`
succeeds; later `getReports` → `getReportDocument(id)` is sent with the "verified no PII" stamp. (Amazon should still
demand an RDT for a restricted document, so the likely outcome is a 403, but the client's fail-closed claim is false
and D11 rests on Amazon.) Fix: apply `isPiiReportType` to `createReportSchedule` too, and make `getReportDocument`
require the report type (e.g. `fetchDocument(sp, scope, reportType, …)` passes it, the guard refuses PII types and
refuses when absent).

**M2 — `SH_AMAZON_MODE` defaults to `production`, and `sandbox` sends Ads writes to the live host (D30 OPEN).**
`packages/amazon-core/src/regions.ts:57` (`value ?? "production"`), `regions.ts:66` (Ads ignores mode).
Failure: a dev or CI process with a vault credential and no `SH_AMAZON_MODE` talks to production; with
`SH_AMAZON_MODE=sandbox` a slice's `SPCreateCampaign` goes to `advertising-api.amazon.com` for real. Conventions §7
says config fails closed. Fix: no default — an unset mode is a boot error (the orchestrator adds the name to
`.env.example`/config); in `sandbox` mode refuse every Ads operation that is not idempotent/read (`OperationUsageError`)
unless an explicit opt-in flag is passed (the `sandbox.ts` script only reads, so it keeps working).

**M3 — a 207 item Amazon did not mention is marked `retryable: true`, also for writes.**
`packages/amazon-core/src/batch.ts:122-128`. Failure: `SPCreateCampaign` batch of 10; Amazon creates all 10 but the
body is truncated/unparsable or omits indices → 10 × `missing_result, retryable: true`; the command executor retries
and creates 10 duplicate campaigns. ADR-0006/0011: a write whose outcome is unknown is reconciled by re-reading, never
blindly repeated. Fix: pass the operation's idempotency into `mapMultiStatus` (or let `ads.batch` post-process) and
mark missing items `outcome_unknown`, `retryable: false` for non-idempotent operations.

**M4 — EX-PORTFOLIOS writes bypass the 207 mapping.**
`packages/amazon-ads/src/v0/ex-portfolios/index.ts:107-110`. `create`/`update` return the raw response body of
`CreatePortfolios`/`UpdatePortfolios` (both 207, batch 100, `catalog/ads/operations.json`), so a caller sees a 2xx
and a body; nothing forces per-item handling, and there is no `batchMax` chunking. Also the v0 SP-v3 style
`Prefer: return=representation` header that ADR-0006 names is never sent anywhere (`git grep -i prefer` → none), so
success items carry only ids. Failure: create 150 portfolios → one request over `batchMax` (Amazon 400s the whole
call), or a 207 with 3 errors treated as done. Fix: implement `create`/`update` with `ads.batch(…)` returning
`BatchResult`, and send `Prefer: return=representation` for v0 batch writes (from the catalogue `headers`).

## May fix later (→ BACKLOG follow-ups)

**S5 — SP-API LWA endpoint follows the Ads regional table.** `regions.ts:31,37`: EU/FE SP-API tokens are exchanged at
`api.amazon.co.uk` / `api.amazon.co.jp`. The table source (`docs/discovery/ads-domains.md` §1) is Ads-specific; the
official SP-API SDK always uses `https://api.amazon.com/auth/o2/token`
(`refs/amazon/selling-partner-api-sdk/javascript/sdk/helper/LwaAuthClient.mjs:82`). If the regional host rejects SP
credentials, every EU/FE SP call fails at token time. Cannot be verified offline (D30): make `lwaToken` per API family
(SP → `api.amazon.com`) or verify in P3-SMOKE.

**S6 — report gate key is global, not per client app.** `packages/amazon-ads/src/reports.ts:296` default
`"ads:v1-reports"` has no app fingerprint (and no tenant prefix). With one app per deployment it is right; with several
Ads apps (self-host vs SaaS, D-shape ADR-0014) one app's report blocks another's. Default the key to
`ads:v1-reports:<appFingerprint>`. Fair round-robin across tenants is also still missing (acknowledged; P3-INGEST).

**S7 — limiter budget is per internal seller account, not per Amazon selling partner.** `rate-limit.ts:208` keys by
`tenantId` + internal `sellerAccountId`. Amazon limits per (app, selling partner, operation): the same Amazon account
connected in two tenants gets two full budgets → 429s. Key by the Amazon merchant/advertiser id when IDENTITY exposes it.

**S8 — 401 refresh only on the very first attempt.** `client.ts:306-316` requires `stats.retries === 0`
(`!forcedRefresh` is always true there, line 241 resets it). A token revoked/rotated during a 429 backoff sequence
yields `AmazonAuthError` instead of one refresh. Track "already force-refreshed" in its own flag.

### New observations (may fix later, not blocking)

- **R1 — replay mode does not pin the host.** If `SH_AMAZON_MODE` is unset and a composition root passes a real transport (`createAmazonRuntime({ credentials, transport: createFetchTransport() })`), mode resolves to `replay` but `baseUrlFor` still returns the production hosts (`regions.ts:69-72`). The sandbox write guard does not apply in replay mode, so calls go live. The default path (no transport passed) fails at boot as intended, so this needs a deliberate wrong wiring. Fix: in `replay` mode, use a non-routable base URL (e.g. `https://replay.invalid`) or refuse a transport that is not a fixture transport.
- **R2 — `getReportDocument`'s `reportType` is the caller's word.** That is acceptable: it is an explicit statement checked against the PII list, fail-closed when absent, and Amazon still demands an RDT for restricted documents. A slice that reads document ids from `getReports` should pass the type that `getReports` returned, not a constant. Note this in the amazon-sp README when convenient.
